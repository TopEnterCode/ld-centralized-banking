Central governance

One typed registry and provider boundary standardize evaluation metadata without coupling services to the vendor SDK.

⌁

Local resilience

Short timeout, retry, circuit breaker, and documented local defaults stop a control-plane issue from becoming a banking outage.

Privacy by design

Only synthetic context attributes are used. Server SDK keys and API tokens never cross the Java boundary.

PRESENTER NOTES

What each scenario proves

Use the controls in order; each scenario changes behavior immediately without deployment or restart.

01

Individual & segment targeting

Select Somchai for the employee rule, Mali for the pilot cohort, or target exactly one synthetic key. The reason is explicit in the timeline.

02

Stable percentage rollout

The 100-user grid uses deterministic SHA-256 bucketing in Mock Mode. Repeating the same percentage keeps every user's assignment stable.

03

Four-stage API migration

Shadow returns v1 while comparing v2. Live returns v2 while comparing v1. Complete removes the dual call. The route is visible end-to-end.

04

Kill switch

Disabling payment v2 makes v1 authoritative immediately—even if migration is Live or Complete. It is a safety control, never authorization.

05

Failure without cascading

Provider failure uses SDK defaults; DTM timeout or outage opens service circuit breakers and uses local defaults. The UI says degraded instead of claiming success from LaunchDarkly.

06

Credential separation

The browser receives only a client-side ID and one allowed flag. The SDK key remains in DTM; the API token is reserved for guarded server-side administration.

Important boundary

Feature flags control feature delivery and routing. They do not authenticate customers, authorize payments, validate limits, or replace transaction controls.
